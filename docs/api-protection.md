# API request protection

All three applications use a native API-wide limit of 300 requests per 60 seconds per trusted client IP, per Worker environment. Municipal namespaces are local 2004, preview 2005, production 2006. Every HTTP fetch counts once, including health, unknown paths, unsupported methods, preflight and rejected origins. There is no owner/authentication bypass. Internal scheduled work is outside HTTP admission. Counters are approximate and local to Cloudflare locations, not strict global quotas; shared NAT/cross-zone caller addresses share capacity.

Platform references: [native rate-limit binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) and [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/). Installed Wrangler 4.158.0 schema and generated declarations are the local compatibility baseline; dry runs verify packaging rather than live admission behavior.

Admission happens before authentication, body parsing or D1/provider effects. The bounded key is `api:v1:` plus a SHA-256 digest of the canonical trusted `CF-Connecting-IP` literal; missing, invalid or oversized metadata shares one sentinel bucket. IPv4 requires canonical decimal octets, IPv6 uses the platform URL parser, and literals are at most 45 characters. Other headers, paths, queries and identities cannot select buckets. Never log the IP or digest. Trust assumes the deployed custom-domain ingress, disabled workers.dev/preview URLs and no arbitrary public same-zone forwarding Worker; adding such a proxy requires reassessment. Local fixtures do not prove deployed header spoof resistance.

Only explicit native `success: true` admits. Denied requests return JSON 429 `rate_limited`; missing, malformed, thrown, rejected or stalled binding calls return 503 `rate_limit_unavailable`. Both use `Retry-After: 60`, no-store and normal security/CORS headers; permitted CORS exposes Retry-After. HEAD has no body. The guard deadline is 1000ms. Native calls cannot be cancelled, but late completion/rejection cannot dispatch business work. There is no custom counter, retry loop or fail-open flag.

The read-only frontend handles JSON and HTML 429 with manual retry guidance even without readable Retry-After. It preserves cancellation and never repeats requests automatically. Opaque fetch/CORS errors mean connectivity is unavailable, not proof of throttling. This application currently exposes no mutation helper; any future write helper must explain uncertain write outcomes and ask users to check state before repeating an opaque failure.

The shared zone WAF policy owned by the portfolio coordination record covers `/api` and `/api/` paths at 120 requests per 10 seconds, with 10-second mitigation. It shares IP capacity across applications/environments and can return the default Free-plan HTML 429 without CORS or Retry-After. WAF staging stays disabled until the affected client fixes are released and verified. No intentional live bursts are authorized. See the parent API-protection task/plan evidence for the exact desired rule and unchanged unrelated controls.

## Diagnostics and release conditions

Each blocked request emits at most one fixed structured guard event containing event, numeric status, outcome and fixed reason. It never includes address, digest, identity, token, body, request path/query/method or exception/provider text. Successful requests emit no guard log. Existing persistent observability remains disabled: local console tests do not establish that automatically collected metadata is safe.

Before enabling a persistent sink in preview, inspect the actual collected metadata with synthetic path/query/token markers and prove the markers absent. The supported candidate is query redaction enabled, invocation logs disabled, traces disabled, and bounded platform head sampling (for example 0.1), within the existing included capability. Do not blindly activate a sink, add paid services or create a recipient/test send. Native request/status metrics plus sampled fixed events are intended diagnostic inputs; routine 429 is aggregate capacity monitoring. Sustained returned 503 needs an existing actionable operator route and an exercised notification path. No such route has yet been established: OPS-OBS-04 and actual sink privacy/operation remain release blockers. Absence of exceptions is not evidence that returned 503 is detected.

Release preview first only after approval, read back the binding/namespace/limit and ingress configuration, and use ordinary read-only requests for health/security/latency evidence. Do not remove production bindings or use business mutations to force failures. Actual ordinary attributable WAF enforcement/recovery and deployed latency remain unverified until observed safely. Keep the prior deployment identifier; roll back the Worker deployment if admission causes an incident and verify ordinary health/auth behavior. Do not disable auth or silently fail open. WAF rollback disables only the owned rule and requires readback, preserving unrelated US/Access controls. No schema or stored-data changes accompany this feature.

## Local checks

`npm run quality` remains the local/CI gate with the configured active `.githooks/pre-push`. Implementation uses focused backend guard/auth/routing tests, frontend API tests, configuration tests, `npm run cf:types`, `npm run cf:types:check`, lint/typecheck and named preview/production dry-run builds. The repeatable warmed synthetic guard benchmark in `request-protection.test.ts` uses 30 warmups and 200 samples with an immediately resolving native mock, excluding business work; p95 target is below 10ms. This is not deployed latency or native service throughput. Combined cross-application rolling-window workload evidence is parent-owned.
